01 · Executive overview

Three products, one platform

Don't think of these as three separate tools you buy. Think of them as three layers of the same system. Each layer sits on top of the one below it and makes it more valuable — the platform holds everything, security wraps around it, and AI accelerates the people using it.

🏢
The foundation

GitHub Enterprise

Where your code, teams, automation, and governance live. Repositories, organizations, permissions, Actions, Codespaces, Packages, Projects, audit logs and policy — the ground everything else stands on.

“The operating system for software development.”
🛡️
The protection layer

GitHub Advanced Security

Security woven directly into the same place developers already work. It scans code, catches leaked secrets, watches your dependencies, and gives security teams a single view of risk — without leaving GitHub.

“A security team continuously inspecting your code.”
🤖
The acceleration layer

GitHub Copilot Business

AI that works alongside every developer — completing code, answering questions, explaining unfamiliar files, drafting tests and docs, reviewing pull requests, and taking on multi-step tasks as an agent.

“An AI pair programmer for every developer.”
How the three layers stack: the platform holds your work, security surrounds it, and AI speeds up the people on top.
🧩

They share one home

All three live in the same place. Security findings appear on the same pull request Copilot helped you write — no context-switching between tools.

🔁

They reinforce each other

Copilot can help fix the vulnerabilities Advanced Security finds, inside the workflow Enterprise governs. The loop closes itself.

📈

Value compounds

Enterprise alone is powerful. Add security and you ship safer. Add Copilot and you ship faster and safer — the whole is greater than the parts.

02 · The foundation

GitHub Enterprise

What it is: the enterprise-grade version of GitHub — the platform where an entire organization's code, collaboration, automation, and governance live under one roof. Why it exists: a single developer needs a repo; a 5,000-person company needs identity, permissions, policy, auditability, and scale. Enterprise turns "GitHub" into something a large regulated organization can safely run its whole engineering function on.

🧠

The one idea to hold onto

Everything below is really answering three organizational questions: Where does the work live? (repos, packages, projects) · Who can do what? (orgs, teams, permissions, EMU) · How do we stay in control? (policies, audit logs, governance). Automation (Actions) and environments (Codespaces) sit on top of that.

📦

Repository management

The core unit: a repo holds your code, full history, issues, and settings. Enterprise adds branch protection, rulesets, required reviews, and CODEOWNERS so critical code can't change without the right eyes on it.

👥

Organizations & teams

An organization groups repos and people; teams mirror your real reporting structure. Grant access to a team once and every member inherits it — nested teams cascade permissions down.

🔑

Permissions & access control

Role-based access from read → triage → write → maintain → admin, at repo, team, org, and enterprise levels. The principle: give the least access needed, managed at the team level, not per person.

🪪

Enterprise Managed Users (EMU)

User accounts are created and fully controlled by your identity provider (Entra ID, Okta). Employees sign in with corporate SSO; accounts are provisioned/deprovisioned automatically and can't reach the public GitHub outside your enterprise.

☁️

Cloud vs Server

Enterprise Cloud is GitHub-hosted (github.com or a dedicated data-residency instance) — always up to date, least ops. Enterprise Server runs in your own datacenter for maximum control. Same core product, different hosting model.

📋

Policies & governance

Enterprise-wide guardrails: which Actions can run, whether repos can be public, 2FA enforcement, allowed IPs, base permissions. Set the rules once at the top and they apply to every org beneath.

🧾

Audit logs

An immutable record of who did what, when across the enterprise — permission changes, secret access, setting edits. The backbone of compliance (SOC 2, ISO) and incident investigation; streamable to your SIEM.

⚙️

Actions (CI/CD)

Built-in automation triggered by events (push, PR, schedule). Build, test, and deploy in workflows defined as YAML in the repo. Enterprise adds runner governance, larger/self-hosted runners, and org-level reuse.

💻

Codespaces

Full, ready-to-code dev environments in the cloud, defined in the repo and launched in seconds. New hires are productive on day one; environments are consistent, disposable, and centrally governed.

📥

Packages

A private registry for the artifacts you produce — npm, Maven, NuGet, containers, and more — living next to the code that builds them, with the same permission model.

📊

Projects

Flexible planning boards, tables, and roadmaps linked directly to issues and pull requests. Work status updates itself as the underlying code moves, so plans reflect reality.

🔌

Integrations

A vast marketplace plus a REST/GraphQL API and webhooks connect GitHub to Jira, Slack, Teams, ServiceNow, cloud providers and internal tools — so GitHub becomes the hub, not an island.

🏢

How this fits a real enterprise organization

Picture a bank with 3,000 engineers. EMU + SSO means every developer signs in with their corporate identity and loses access automatically the day they leave. Orgs and teams mirror the payments, lending, and mobile departments. Rulesets and CODEOWNERS ensure no change to payment code merges without two senior reviews. Actions runs the pipelines, Codespaces gives every dev an identical environment, Packages stores internal libraries, Projects tracks delivery, and audit logs give auditors the evidence trail they require — all in one governed platform.

03 · The protection layer

GitHub Advanced Security

The core idea: the cheapest bug to fix is the one caught before it merges. Advanced Security (GHAS) moves security left — into the pull request, right where developers already work — instead of leaving it to a scan weeks later or a pen-test before release. Below, each capability is broken down the same way: what it does, why it matters, when you use it, the problem it solves, and a real example.

🔍

Code Scanning

Find bugs in your own code
WhatAutomatically analyzes your source for security flaws (SQL injection, XSS, path traversal) as code changes.
WhyVulnerabilities caught in a PR are cheap; the same flaw in production is a breach.
WhenOn every push and pull request, automatically.
Solves"We didn't know that code was insecure until it was already live."
ExampleA dev builds a search box using string concatenation. Code scanning flags a SQL-injection risk on the PR before a human reviewer ever sees it.
🔑

Secret Scanning

Catch leaked credentials
WhatDetects API keys, tokens, and passwords committed to repos — and push protection can block them before they land.
WhyA single leaked cloud key can cost a fortune or expose customer data within minutes.
WhenAt push time and continuously across history.
Solves"Someone accidentally committed the production AWS key."
ExampleA dev pastes an AWS secret into a config file and pushes. Push protection rejects the push instantly and tells them exactly which line to remove.
📥

Dependency Review

Vet new dependencies
WhatShows, right in the pull request, which dependencies a change adds/updates and whether any carry known vulnerabilities or risky licenses.
WhyMost modern code is other people's code — a bad dependency is your problem the moment you add it.
WhenDuring code review, before you merge.
Solves"We pulled in a library that quietly introduced a critical CVE."
ExampleA PR bumps a package to a version with a known high-severity CVE. The review tab flags it red, so the reviewer asks for a safe version before approving.
🤖

Dependabot

Keep dependencies patched
WhatWatches your dependencies for vulnerabilities and opens automated pull requests that bump them to fixed versions.
WhyStaying patched is tedious and easy to forget; Dependabot never forgets.
WhenContinuously in the background, and the moment a new advisory drops.
Solves"We were breached through a known bug that a patch had existed for."
ExampleA new advisory lands for a logging library. Overnight, Dependabot opens a PR upgrading it and links the release notes — the team just reviews and merges.
📊

Security Overview

See all risk in one place
WhatAn org- and enterprise-wide dashboard aggregating every alert — code, secret, and dependency — across all repositories.
WhySecurity teams need the big picture, not one repo at a time.
WhenFor reporting, prioritization, and tracking risk trends over time.
Solves"We have no idea what our overall security posture actually is."
ExampleA security lead opens the overview, sorts by severity, and sees that 12 repos share the same critical alert — so they fix the root cause once.
📣

Security Campaigns

Drive fixes at scale
WhatLets security teams bundle a set of related alerts and hand them to the right dev teams as a tracked, coordinated remediation effort.
WhyFinding problems is easy; getting hundreds of them actually fixed across many teams is the hard part.
WhenDuring a coordinated push to clear a class of vulnerabilities.
Solves"Alerts pile up but nobody owns fixing them."
ExampleA campaign groups every instance of a risky pattern and routes each to its owning team with context — often with Copilot Autofix suggestions attached.
🔗

Supply Chain Security

Trust what you ship
WhatThe umbrella over your software supply chain — the dependency graph, advisory database, SBOMs, and artifact/build provenance (attestations).
WhyAttackers increasingly target dependencies and build pipelines, not just your code.
WhenWhenever you need to prove what's inside and where it came from.
Solves"A customer/regulator asked for an SBOM and we couldn't produce one."
ExampleBefore a release, the team exports an SBOM listing every component and generates build attestations proving the binary came from trusted CI.
🧬

CodeQL

The engine behind code scanning
WhatGitHub's semantic analysis engine that treats your code as a queryable database, tracing how untrusted data flows through it to find deep vulnerabilities.
WhySimple pattern-matching misses real bugs; CodeQL follows data across functions and files.
WhenPowers code scanning by default; security engineers can also write custom queries.
Solves"Our old scanner drowned us in false positives and missed the real ones."
ExampleCodeQL traces user input from an HTTP handler, through three helper functions, into a database call — and flags the injection a regex would never catch.
🛠️

Vulnerability Management

From alert to closed
WhatThe lifecycle around every alert: triage, prioritize by severity, assign, track, dismiss with a reason, and verify the fix — often accelerated by Copilot Autofix.
WhyA finding nobody acts on is just noise; the value is in closing the loop.
WhenEvery day, as alerts arrive and get worked down.
Solves"We find vulnerabilities but can't tell which matter or whether they're fixed."
ExampleA critical alert appears; Autofix proposes a patch as a PR, a reviewer approves it, and the alert auto-closes once the fix merges — fully tracked.
💡

The through-line

Notice the pattern: GHAS meets developers where they already are — in commits, pushes, and pull requests — and gives security teams a single pane of glass above it. Detection (scanning) + prevention (push protection) + remediation (Dependabot, Autofix) + visibility (overview) = security that keeps pace with development instead of blocking it.

04 · The acceleration layer

GitHub Copilot Business

What it is: an AI assistant embedded across the developer workflow — in the editor, on GitHub.com, in the CLI, and in pull requests. Why it matters: developers spend huge amounts of time on boilerplate, context-gathering, and understanding unfamiliar code. Copilot compresses that so people spend more time on the hard, creative parts. The Business tier adds org-wide policy, license management, and the guarantee that your code isn't used to train the models.

🧠

The mental model for how Copilot "knows" things

Copilot is only as good as its context — the information it can see when it answers. That context is assembled from your open files, the surrounding code, the repository, and what you explicitly point it at. Everything below is really about giving it better context and choosing the right mode for the task.

⚡

Code Completion

The original superpower
WhatSuggests the next line, block, or whole function as you type — grey "ghost text" you accept with Tab.
HowJust keep coding; write a clear function name or comment and let it draft the body.
WhyRemoves boilerplate and keeps you in flow instead of reaching for docs.
WhereIn the editor, during the Coding phase.
💬

Chat

Ask your codebase anything
WhatA conversational assistant that answers questions, generates code, and explains errors in natural language.
HowAsk "why does this test fail?" or "write a function that…"; reference files with #.
WhyTurns "search Stack Overflow and hope" into a direct answer grounded in your code.
WhereEditor, GitHub.com, mobile, CLI — throughout the workflow.
🎯

Agent Mode

From suggestion to action
WhatCopilot takes a high-level goal and executes multi-step work itself — editing across files, running commands, and iterating until done.
HowGive it a task ("add pagination to the users API"); it plans, edits, and can even open a PR.
WhyHandles whole tasks, not just lines — you review the result instead of typing every keystroke.
WhereEditor and GitHub, for larger Coding tasks and issues.
🧩

AI Context

Why answers are relevant
WhatThe information Copilot gathers to ground a response: open tabs, nearby code, the repo, and anything you attach.
HowKeep relevant files open and attach the right ones; better context = better answers.
WhyIt's the difference between a generic snippet and one that fits your conventions.
WhereUnderpins every other feature on this page.
📖

Code Explanation

Understand fast
WhatPlain-language walkthroughs of what a file, function, or regex actually does.
HowSelect code and ask "explain this"; great for legacy or unfamiliar areas.
WhyOnboarding and code archaeology go from days to minutes.
WhereAny time you meet new code — Coding & Review.
🔀

Pull Request Assistance

Better PRs, faster review
WhatDrafts PR descriptions from the diff and provides an AI reviewer that comments on changes and suggests fixes.
HowOpen a PR and let Copilot summarize it / request a Copilot review.
WhyClearer PRs and a first-pass review mean humans focus on what matters.
WhereThe Review phase, on GitHub.
📝

Documentation Generation

Docs that keep up
WhatGenerates docstrings, READMEs, and inline comments from the code itself.
HowAsk Copilot to "document this function/module."
WhyDocs are the first thing skipped under deadline; Copilot removes the excuse.
WhereCoding and before Review.
🧪

Test Generation

Coverage without the grind
WhatWrites unit tests, including edge cases you might not think of, in your existing test framework.
HowSelect a function and ask "write tests for this."
WhyMore coverage, less tedium — and tests double as living documentation.
WhereThe Testing phase.
🗂️

Workspace Context

Reason over the whole repo
WhatLets Chat consider the entire project, not just the open file, so it can answer "where is X handled?" across the codebase.
HowUse repo/workspace-wide chat and ask architecture-level questions.
WhyReal questions span many files; whole-repo awareness makes answers trustworthy.
WherePlanning, debugging, and onboarding.
🔌

Extensions

Connect your tools
WhatBring third-party and internal systems (Jira, Datadog, Sentry, your own APIs) into Copilot Chat so it can act with that context.
HowInstall/build extensions; ask Copilot to pull an incident or ticket inline.
WhyCopilot becomes a hub across your whole toolchain, not just the editor.
WhereAcross the workflow, wherever you use Chat.
🧠

Models

Pick the right brain
WhatCopilot offers a choice of underlying AI models, each with different strengths in speed, reasoning depth, or cost.
HowSwitch models in Chat — a fast one for quick edits, a deeper one for tricky reasoning.
WhyMatching the model to the task balances quality against speed and spend.
WhereAny Chat or agent interaction.
📄

Prompt Files

Reusable, shared instructions
WhatVersion-controlled files (e.g. custom instructions / .prompt files) that encode standing guidance — coding standards, preferred patterns, task templates.
HowCommit them to the repo so every teammate's Copilot follows the same rules.
WhyTurns "prompt engineering" into a team asset instead of tribal knowledge.
WhereSet once, applied across all Coding work.
🚀

Where Copilot pays off in the workflow

Read the "Where" line on each card and a shape appears: Copilot isn't one feature at one moment — it threads through planning (workspace questions), coding (completion, agent mode, docs), testing (test generation), and review (PR summaries and AI review). The productivity gain isn't just typing speed; it's spending less time stuck — understanding, searching, and context-switching.

🏢

= the operating system for software development

It's the environment everything runs on: it manages "users," "permissions," "storage" (repos), and "processes" (Actions). You don't think about it constantly — but nothing works without it.

📖 Glossary

Repository (repo)
A project's container — its code, full version history, issues, and settings.
Organization
A shared account that groups repositories, people, and teams under one entity.
Team
A group of members inside an org used to assign access in bulk; can be nested.
Enterprise Managed User (EMU)
A GitHub account created and controlled by your company's identity provider via SSO.
Pull Request (PR)
A proposal to merge changes, with review, discussion, checks, and approval.
Branch protection / Ruleset
Rules that gate changes to important branches (required reviews, checks, no force-push).
CODEOWNERS
A file mapping paths to the people/teams who must review changes there.
GitHub Actions
Event-driven automation (CI/CD) defined as YAML workflows in the repo.
Codespaces
Cloud-hosted, ready-to-code development environments defined by the repo.
Audit log
An immutable record of who did what and when across the org/enterprise.
Code Scanning
Automated analysis that finds vulnerabilities in your own source code.
